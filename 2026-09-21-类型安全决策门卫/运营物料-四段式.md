## 二、评论首评（发文后自己占沙发）

先占个楼，说个真事。我之前写工具门卫的时候，把 shell 和删文件的放行阈值都设成 0.9，以为万事大吉。后来跑阈值扫描才发现，统一阈值下，要么高危工具上太松、要么低危工具上太紧，根本没有两全点。我把代码里那一行 `safety_prob >= threshold` 单独拎出来扫了一遍 0.5 到 1.0，误放行率和误拦截率此消彼长，清清楚楚。

这事儿不是我瞎编。Jev 标榜校准概率、放心自动执行，但独立测试给的结论是谨慎的：开发者 Emil Lindfors 用 192 个是非判断做粗略校准检查，概率区间和真实命中率方向一致，但两端略保守；TypeSafe 自报的四个工作流基准，参考答案是 GPT-6 Astra 和 Claude Fable 5.1 的平均值，不是独立真值，所以那个 67.8% 不能直接读成准确率。

你们团队门卫代码里那个阈值写在哪？是不是所有工具共用一个值？评论区聊聊。正文里给了两个不联网不装包就能跑的脚本，自己扫一遍就知道你的阈值现在站在曲线的哪个位置。

## 四、本篇做了什么，对谁有用

做了什么：
用刚发布的 Jev（TypeSafe AI，2026-09-15 发布，前 OpenAI 研究员 Diogo Almeida 带队，4000 万美元种子轮）作切入点，只讲透一件事：把它接进 Agent 循环给危险工具调用当门卫时，最致命的不是没接上，而是把校准概率误当成布尔、阈值定错（误拦截、误放行、校准不等于准确、要分级）。给了两张可运行脚本（门卫统计 + 阈值扫描，含 self-test，纯标准库、可注入假后端）、四张手写配图和两张脚本真实运行输出的截图，所有数字均来自一手或独立可核查来源，文末列了「本文不承诺什么」（193.6 倍上限、67.8% 基准存疑、RLCD 无论文）并附了完整的一手与独立来源清单（含 Every 的 777 次判断实测、lindfors.no 的 192 个判断校准分箱）。

对谁有用：
1. 正在给 Agent 接工具层、想用廉价模型做风险门控的后端和平台工程师
2. 技术负责人，以为门卫接上 Jev 就安全，本文专治这个错觉
3. 用 LangChain AutoModeMiddleware 之类做工具路由的开发者，想知道分级阈值怎么落地
4. 关注 AI 基础设施新零件、想搞清 Jev 到底能干嘛不能干嘛的人
