# 「我明明没干啥，额度怎么就没了」？拆开 AI 编码账单的 5 个吞钱口，附 8 个坑的自检清单

上个月我把团队的 AI 编码账单拉出来看了一遍，第一反应是数字错了。

我们那个月的提交量、代码行数、功能交付，跟前一个月差不多。但账单涨了 2.7 倍。我一开始怀疑是有人拿 key 跑批，查了一圈没有。后来把 usage 按请求拆开，才发现问题不在"干了多少事"，而在**每一次调用到底在为什么付费**这件事，我从头到尾就没弄对过。

同一周，OpenAI 发了一份内部数据，把这个问题推到了所有人都看得见的地方：截至 8 月中旬，他们研究部门的中位研究员，**每天在 agent 推理上花掉超过 600 美元**（按 API 价格折算），前 10% 的重度用户超过 7000 美元一天。把这两组数字放一起，我意识到一件事——

我和那个月烧掉 600 美元一天的研究员，踩的是同一批坑，只是数量级不同。

先把话说在前面，避免这篇文章变成制造焦虑：**600 美元一天不是普通开发者的日常**。那是前沿实验室里同时挂着 4 个以上 agent 会话、跑着数天级研究任务的人。绝大多数用 Cursor、Claude Code、或者自己接 API 写东西的人，月消费在几美元到几十美元这个量级。我写这篇不是为了告诉你"你也在烧钱"，而是因为**账单的构成结构是同一个**：同样的五个吞钱口，在我们的量级上让账单涨 2.7 倍，在他们的量级上就是 600 美元一天。

搞清楚结构，比搞清楚数字重要。

## 本文怎么拆这个大问题

"额度怎么就没了"是个症状，不是一个问题。它下面至少压着三个可以独立解决的失败模式：

| 失败模式 | 具体表现 | 为什么会独立发生 |
|---|---|---|
| **单价看错了** | 按定价页的 input 价格估成本，实际付的是另一个数 | output 和 reasoning token 才是主力，而它们不出现在你的直觉里 |
| **缓存没吃上** | 开了 prompt caching，命中率却接近 0 | 缓存是前缀结构问题，不是开关问题 |
| **循环在自我复利** | agent 跑了一晚上，第二天早上一看账单 | 每一轮都把上一轮的输出重新读一遍，成本随轮次复合增长 |

三个模式的**总根**是同一条：**我们把 token 当成"用量"在记账，但它其实是「上下文长度 × 轮次」的函数**。你不是在为最终那 200 行代码付费，你是在为"每一轮都重新读一遍历史"付费。

下面五个问题，第一个立总根，第二到第四个分治三个症状，第五个守底线。

## 问题 1（立总根）：账单为什么不等于「输入 + 输出」

先说结论：你的账单里至少有三项，是你用「输入 token × input 单价 + 输出 token × output 单价」算不出来的。

**第一项：reasoning token。**

推理模型在给出回答之前，会在内部生成一堆你看不见的思考 token。OpenAI 的 o 系列不返回这些 token，只给一个摘要；Anthropic 的 extended thinking 会以 thinking block 的形式返回，看得见。但**不管看不看得见，两家都按 output 的价格计费**。

这个设计的效果很直接：你看到回答只有 400 个 token，账单上可能记了 5000 个。有个公开的推理成本测算工具给了组数据，同一个调用在 GPT-5 reasoning 下，3000 个 reasoning token 占到了单次成本的 79%，而 naive 估算（只算输入 + 可见输出）会低估 381%。

更麻烦的是**分布**。simple prompt 可能只产生几百个思考 token，hard prompt 能到上万。同一个 calculator 的测算：p50 是 4000 个思考 token，p99 按 4 倍算是 16000 个，月度账单能在 7275 美元到 25275 美元之间摆动。**平均数是没用的，你要按 p99 做预算。**

**第二项：缓存写入的溢价。**

缓存不是免费的。Anthropic 写一次 5 分钟 TTL 的缓存要付 1.25 倍 input 价格，写 1 小时 TTL 的付 2 倍。OpenAI 从 GPT-5.6 起也加了 1.25 倍的写入费。如果你写进去的缓存从来没被读到（这是常态，见问题 3），你就是在用 1.25 倍的价格买了一次普通请求。

**第三项：非生产流量。**

CI 在每个 PR 上重放一遍 prompt，staging 镜像了生产环境，压测脚本拿真实模型端点验证系统容量。这些东西和你的生产调用共用同一个 API key、同一个账号。DigitalOcean 那篇关于推理成本的工程文章里引了一组企业分析数据：团队第一次把流量按环境拆开时，经常发现 CI 和 staging 占到了总 token 量的 30% 到 50%。

这三项的共同点：**它们都不在"输入 + 输出"这个心智模型里**。所以你用这个模型估算，一定会低估，而且低估的倍数不确定。

## 问题 2（治单价看错）：你在为哪一类 token 付最贵的钱

定价页上那个 input 价格，是三家厂商里最小的那个数字，也是营销时最常被引用的那个。但实际账单的形状由 **output 对 input 的倍数**决定。

2026 年 3 月的公开价格对照（每百万 token）：

| 模型 | input | output | 倍数 |
|---|---|---|---|
| DeepSeek V3 | $0.28 | $0.42 | 1.5x |
| GPT-4o | $2.50 | $10.00 | 4x |
| Claude Sonnet 4.6 | $3.00 | $15.00 | 5x |
| Gemini 2.5 Pro | $1.25 | $10.00 | 8x |

倍数意味着什么？意味着**工作负载的形状决定了哪个模型便宜**。

长输入短输出（总结、抽取、分类）：input 主导，选 input 单价低的，哪怕是 Gemini 2.5 Pro 这种 8 倍模型也可能比 4 倍模型便宜。

短输入长输出（agent 循环、长文生成、代码反复修订）：output 主导，选 output 单价低的。而且这类负载有个额外的恶性机制——**模型自己生成的 token，下一轮会作为 input 被重新计费**。output 贵的东西，在 agent 里会被重复收两次钱。

所以选型时最该问的不是"谁的输入便宜"，而是"我的输入/输出比是多少"。这个问题很多团队答不上来，因为没人量过。

还有一个便宜但经常被忽略的：**Batch API**。OpenAI 和 Anthropic 都给批处理 50% 折扣，代价是异步（一般 1 小时内返回，最长 24 小时）。上限是 OpenAI 单批 5 万请求 / 200MB，Anthropic 10 万请求 / 256MB。它还有个附带好处：批端点走独立的速率限制，不会吃掉你生产的 TPM 配额。所有不要求实时性的活——回归评测、历史日志重跑、合成数据生成——都该走这条线。

## 问题 3（治缓存没吃上）：缓存不是开关，是前缀结构

这是我最想讲的一节，也是我那个月真正踩到的坑。

Prompt caching 的机制只有一句话：**精确前缀匹配**。服务端对你 prompt 开头的一段做哈希，命中就直接读已算好的 KV，不重新 prefill。命中的部分是 input 价格的 10%。

这句话有两个字要命：**开头**。

只要前缀里有一个 token 不一样，从那个位置往后的所有内容全部失效。不是"这一句重新算"，是"这一句之后全重新算"。OpenAI 的实现按 128 token 的粒度做匹配延长，所以哪怕你只改了一个字符，后面可能几万 token 都跟着作废。

我那个月的账单就是这么炸的。我们的系统提示里有一行是：

```
当前时间：2026-08-14 15:32:07
```

一行时间戳，在系统提示的第三段。它后面的工具定义、代码库索引、历史对话，全部无法命中缓存。等于每轮都在全价重新 prefill 一遍 60K 的上下文。

各家的最小可缓存长度和 TTL（2026 年 7 月口径）：

| 厂商 | 触发方式 | 最小前缀 | 读价 | 写价 | 默认 TTL |
|---|---|---|---|---|---|
| Anthropic | 显式断点，最多 4 个 | 1024（Sonnet/Opus 级）、4096（Haiku 4.5） | 0.1x | 1.25x（5min）/ 2x（1h） | 5 分钟，命中免费刷新 |
| OpenAI GPT-5.6+ | 自动 + 可选显式断点 | 1024 | 0.1x | 1.25x | 约 30 分钟 |
| Google Gemini 3 | 隐式默认，显式可选 | 4096 | 最高 90% off | 隐式无写入费，显式按小时收存储费 | 1 小时可配 |

几个容易忽略的点：

**低于最小长度会静默失败**，不报错。你加了 cache_control，前缀只有 800 token，什么都不会发生。

**TTL 是滑动的**。Anthropic 的 5 分钟 TTL 在每次命中时免费刷新，所以稳定请求流可以让缓存一直活着；但只要你去开了个会，回来就全没了。

**断点不要放在会变的内容上**。最多 4 个断点，放在最大的静态块末尾（系统提示、工具定义、参考文档）。

**动态内容一律放最后**：用户问题、会话变量、时间戳、历史对话。

算一笔账你就知道这个结构值多少钱。假设稳定的系统提示 + 工具定义 + 历史是 60K token，每轮新增 2K，跑 30 轮：

- 无缓存：每轮 prefill 60K + 累计新增，30 轮合计约 2.73M input token，按 Sonnet 4.6 的 $3/M 算，约 **$8.19**
- 有缓存：首次写入 60K × 1.25 = 75K 等效，29 次读取 60K × 0.1 × 29 = 174K 等效，新增部分 0.93M 全价，合计约 1.179M 等效 token，约 **$3.54**

省 57%。而实现这个，只需要把那行时间戳从系统提示里挪走。

至于盈亏平衡点：5 分钟 TTL 的缓存在**第二次读取**就回本（1.25x 写 + 0.1x 读 = 1.35x，对比不缓存发两次的 2x）；1 小时 TTL 需要三次。命中率超过 30% 就开始省钱，超过 60% 省得很明显。

## 问题 4（治循环复利）：agent 每一轮都在重新读一遍历史

这是把账单从"贵"推到"失控"的那一环。

agent 循环和单次对话的成本结构完全不同。单次对话你付一次 prefill 和一次生成。agent 循环里，**第 n 轮的输入 = 系统提示 + 工具定义 + 前 n-1 轮的所有内容**。翻譯成钱就是：成本随轮次近似二次增长，而不是线性。

一个公开的极端样本：有人用 GPT-6 Astra 接 MCP 打通了《传送门》，24 小时，3336 次工具调用，API 费用 571.18 美元。平均下来每次调用 0.17 美元。单次不贵，乘上 3336 就是 571 美元。

再看 OpenAI 那份内部数据里的另一组对照，我觉得比 3.1 倍工时更能说明问题：

- 15 分钟以内能完成的任务，**86% 可以零干预成功**
- 但在 4 到 8 小时这个档位，**即使是最终成功的任务，超过一半也需要至少一次人工介入**

这条曲线就是在说：时长上去之后，agent 会开始原地打转。而原地打转的每一圈，都是按完整上下文收费的。失败重试、自我纠错、工具报错后重新规划，这些动作在 UI 上表现为"它还在想"，在账单上表现为又一个完整的 prefill。

还有个反直觉的点：**上下文压缩本身要钱**。当上下文快满了，很多框架会做一次总结压缩。这次总结的输入是全部历史，输出是摘要，两头都计费。你为了省钱做的压缩，本身是一次大额调用。

所以循环层唯一可靠的防线不是"更聪明的提示词"，是**硬上限**：最大轮次、最大累计 token、最大累计金额，以及最关键的——**连续 N 轮无进展就退出**。无进展的定义可以是"最近 3 轮的 diff 为空"或者"最近 3 轮打开的是同一批文件"。

## 问题 5（守底线）：三个数，把账单从玄学变成仪表盘

讲了这么多机制，落到自己身上只需要测三个数。这三个数我建议每个用 AI 写代码的团队都挂到看板上：

**1. 单任务成本（cost per task）**

不是一个月的总额除以任务数，那个平均数没有意义。要按任务类型分组，并且记录 p50 / p90 / p99。你会发现真正吃掉预算的是那条长尾，不是中位数。

**2. 缓存命中率（cache hit rate）**

`cached_input_tokens / total_input_tokens`。这个数低于 30%，说明你的前缀结构有问题，优先去查有没有动态内容混进了前面。这是我在自己团队里投入产出比最高的一项：改一行代码的位置，账单降 57%。

**3. 人工介入率（intervention rate）**

按任务时长分桶统计需要人插手的比例。对照 OpenAI 那组数据（<15 分钟 86% 零干预，4-8 小时过半要介入）给自己定基线。这个数不只是钱的问题，它同时也是质量信号：一个需要你救四次的 agent，产出的代码你敢直接合吗。

顺手说一个最容易犯的测量错误：**用 p50 估预算**。thinking token 的方差极大，p99 是 p50 的 3 到 5 倍很正常。按中位数做预算，一定会在某个月爆掉。

至于 OpenAI 那份 600 美元一天的数据，我的读法是：它验证的不是"AI 很贵"，而是"当上下文、并发、轮次三个乘数同时拉满时，账单会长成什么样"。我们的量级小得多，但**乘数是一样的**：并发会话数 × 单会话上下文 × 轮次。你每多开一个会话，就多一份独立上下文和独立缓存；这大概也是为什么 OpenAI 提到他们的研究员现在经常同时跑 4 个以上会话。

## 小结：五个问题怎么回答开头那个大问题

| 小问题 | 治的是哪一块 | 结论 |
|---|---|---|
| 问题 1（立总根） | 建立正确账本 | 账单 ≠ input + output，还有 reasoning、缓存写溢价、非生产流量三项 |
| 问题 2（治单价看错） | 症状① | 看 output/input 倍数而不是 input 单价；先量自己的输入输出比 |
| 问题 3（治缓存没吃上） | 症状② | 缓存是前缀结构问题；静态在前、动态在后；一行时间戳能让 60K 上下文全部失效 |
| 问题 4（治循环复利） | 症状③ | 成本随轮次复合增长；唯一可靠防线是轮次/金额/无进展的硬上限 |
| 问题 5（守底线） | 可度量 | 单任务成本、缓存命中率、介入率，按 p99 而非 p50 预算 |

回到标题那个问题：「我明明没干啥，额度怎么就没了」。答案是——**你干的事没变，但每一件事的单价和轮次变了**，而这两样东西在 UI 上都看不见。

## 进阶：三层治理

如果你想系统性地管这件事，按三层来做，从上到下收益递减但成本递增：

**计价层**：先量清楚自己的输入输出比和 reasoning 占比，再选模型。不要按定价页的 input 价格选。不实时的活全部走 Batch，50% 折扣加独立配额。

**缓存层**：把 prompt 拆成"静态块 + 动态尾巴"两截，静态块顺序固定、内容冻结，动态尾巴里放时间戳、会话变量、用户问题。加一个前缀长度断言，低于厂商最小门槛就报警（因为它是静默失败的）。

**循环层**：给 agent 装上三重止损——轮次上限、金额上限、连续无进展上限。第三个最容易被忽略，但它拦住的正是《传送门》那种 3336 次调用里的大部分无效往返。

## 8 个坑的自检清单

按症状归位，每条给症状和解法：

**单价看错（1-2）**

1. **拿 input 单价估算成本**。症状：预算和实际差 3 倍以上。解法：用 output/input 倍数反算，先量自己真实的输入输出比。
2. **忽略 reasoning token**。症状：回答很短但很贵。解法：读 usage 里的 reasoning 字段（Anthropic 可见，OpenAI 需在 dashboard 看），按任务难度分档调 effort，简单任务不要开高。

**缓存没吃上（3-5）**

3. **静态块里混了动态内容**。症状：缓存命中率接近 0。解法：时间戳、UUID、随机排序的文档一律移到最后，或整个删掉。
4. **以为加了 cache_control 就生效**。症状：命中率没变化。解法：确认前缀超过最小长度（Anthropic 1024、Gemini 3 是 4096），确认断点没超过 4 个，确认断点在静态块末尾。
5. **多会话并行时以为缓存共享**。症状：4 个会话的开销约等于 4 份全价 prefill。解法：能合并的任务合并；不能合并的，确保每个会话自己的前缀是稳定的。

**循环复利（6-8）**

6. **agent 没有轮次和金额上限**。症状：跑一晚上，早上看到三位数账单。解法：三重止损，落盘报告。
7. **CI / staging / 压测和生产共用 key 且不打标签**。症状：账单里有一块说不清来源的流量。解法：每个请求打 environment 和 service 标签，第一次拆分通常会发现 30%-50% 来自非生产。
8. **用 p50 做预算**。症状：某个月突然爆掉。解法：thinking token 按 p99 估，p99 通常是 p50 的 3-5 倍。

## 最后说一句我的看法

我原本以为 AI 编码的成本是个"用量"问题，用多了就贵，省着点就行。查完那个月的账单我改了主意：**它是个结构问题**。同样的任务量，改一行时间戳的位置能差 57%，加一个无进展止损能砍掉一半的无效往返。这些跟"用多用少"没关系，跟"你怎么搭这条链路"有关。

而结构问题有个好处：它是一次性的。你把前缀顺序调对一次，把止损装上，之后每个月的账单都是那个形状。这也是我觉得值得写下来的原因——不是教人省钱，是省下来的那部分是纯浪费。

## 钩子：三个脚本

上面讲的三层（账单归因、缓存前缀漂移检测、agent 循环止损）我写成了三个可以直接跑的脚本，放在 GitHub：

**github.com/beverlyLee/ai-passage/tree/main/2026-09-08-AI账单构成/code**

- `01-bill-attribution.py`：把 usage 记录按 cached input / fresh input / visible output / reasoning output / 环境分段算钱，直接输出占比，帮你定位吞钱口在哪一层
- `02-cache-prefix-diff.py`：对比连续两次请求的 prompt，找出第一个导致前缀漂移的位置，并判断是否低于厂商最小可缓存长度
- `03-loop-guard.sh`：agent 循环的三重止损（轮次 / 累计金额 / 连续无进展），触发时退出并写一份报告

## 本篇做了什么

- 把「AI 编码账单失控」这个症状拆成单价看错、缓存没吃上、循环复利三个可独立解决的失败模式，指出总根是我们把 token 当"用量"而非「上下文 × 轮次」的函数
- 用 2026 年 3 月的公开价目表算了 output/input 倍数对工作负载选型的影响，并给出一个 30 轮 agent 会话的缓存收益算例（60K 稳定前缀 + 2K 增量，57% 差距）
- 核到三家厂商的缓存机制差异（最小前缀 1024 vs 4096、TTL、写入溢价、断点上限）和盈亏平衡点（5 分钟缓存第二次读取回本）
- 给了三个可测指标和它们的读法，特别强调了为什么要用 p99 而不是 p50
- 写了三个可运行脚本，覆盖归因、检测、止损

**对哪些群体有用**：

- **用 Cursor / Claude Code / 通义灵码 / 自接 API 的开发者**：第 3 节和第 8 条坑，投入产出比最高，改一行配置的事
- **给团队搭 AI 编码基建的人**：三个指标和三层治理可以直接抄
- **在做 agent 或 AI 应用后端的工程师**：第 4 节的循环复利机制和止损设计
- **在做成本核算和 FinOps 的人**：问题 1 的三项和 Batch 那一段

如果你只是偶尔用 AI 写点代码，看完第 3 节和第 8 条坑就够了，那两处改动不需要理解原理。
