# code/GPT-6Astra强在哪又怕在哪

两段**纯标准库、可直接运行**的脚本，对应正文里两个最容易被讲空的地方：

| 脚本 | 对应正文 | 作用 |
|---|---|---|
| `01-compaction-loss-simulator.py` | 问题 3（治"记忆"）/ 坑 1 | 同一份会话事件，跑两条记忆管线：旧式确定性 compaction（启发式裁剪+摘要）与 Astra 的 Structured Searchable Notes。前者在窗口压缩时把「只被某条工具输出按值携带」的易失环境状态（TMPDIR / 环境变量 / socket 句柄）弄丢，后者因为「产生即入索引」而始终可检索 |
| `02-pricing-cliff-calculator.py` | 问题 5（守底线）/ 坑 2·3 | 272K 计费悬崖计算器：验证「整请求重定价」而非只算超出部分；四档费率（Standard / Batch·Flex / Fast）与 272K 上下两段；把缓存输入 $1/M 这个 agent 循环主费率单拎出来算省了多少 |

## 运行

```bash
cd code/GPT-6Astra强在哪又怕在哪

# 脚本1：内置演示会话（默认预算下 compaction 会丢指针、notes 会保留）
python3 01-compaction-loss-simulator.py

# 脚本1：显式跑自检场景（固定为内置演示 + 默认预算，忽略其他参数）
python3 01-compaction-loss-simulator.py --self-test

# 脚本1：换成外部事件流，探测别的易失键
python3 01-compaction-loss-simulator.py --events examples/session_events.jsonl --key TMPDIR

# 脚本1：把预算调大，观察"没触发压缩时两条管线结果一致"
python3 01-compaction-loss-simulator.py --budget 600

# 脚本2：默认三组演示（悬崖 / 缓存省多少 / 最坏 vs 最省）
python3 02-pricing-cliff-calculator.py

# 脚本2：单条请求（输入 缓存输入 缓存写 输出，单位 token）
python3 02-pricing-cliff-calculator.py --req 273000 0 0 60000 --tier standard

# 脚本2：批量样本（JSONL），一次算一排
python3 02-pricing-cliff-calculator.py --json examples/request_samples.jsonl
```

自检的触发条件（这点很容易踩坑）：

- `02` 的默认调用会跑自检；`--req` / `--json` 模式不跑（那是查询，不是验证）。
- `01` **只在「`--events` / `--budget` / `--key` 三个参数全为默认」或显式加 `--self-test` 时**才跑自检。原因很直接：一旦你改了预算或换掉探测键，"compaction 应当丢"这个预期本身就不再成立，硬套默认断言只会把一个正常用法变成 traceback。想看自检就加 `--self-test`，它会强制回到默认场景。
- 两者自检失败都以非 0 退出码结束，可直接挂进 CI。

## 脚本 1 的关键口径

`01` 模拟的是**机制**，不是 OpenAI 内部实现（后者没有公开）。它要复现的因果链只有一条：

> 易失状态只被某条原始工具输出「按值携带」→ 没有任何地方能重新派生它 → 启发式摘要一旦裁掉那条事件，后续步骤永久失忆。

- 触发条件是「窗口 token 估算超预算」，压缩策略是「保留首条 + 摘要 + 末两条」，中间原始事件内容被替换成一句摘要文本，**`volatile` 字段随之消失**——这正是 compaction 的真实风险模型。
- 默认预算 `25` 是特意压小的：内置演示只有约 32 token，预算 600 时永远不触发压缩，也就演示不出丢失（想看"未压缩时两条管线一致"，把 `--budget` 调大即可）。
- `Searchable Notes` 一侧**不参与窗口裁剪**：`volatile` 在事件产生时就写进独立索引，所以窗口怎么压缩都不影响检索。这就是正文那句"不是越写越短的草稿纸，而是带索引的笔记本"的可执行版本。

## 脚本 2 的费率表与两条不变量

每百万 token 单价，`(输入, 缓存输入, 缓存写, 输出)`：

| 档位 | ≤272K | >272K |
|---|---|---|
| Standard | $10 / $1 / $12.50 / $50 | $20 / $2 / $25 / $75 |
| Batch · Flex | $5 / $0.50 / $6.25 / $25 | $10 / $1 / $12.50 / $37.50 |
| Fast | $20 / $2 / $25 / $100 | $40 / $4 / $50 / $150 |

自检里写死了两条不变量，用来防止手抄费率出错（**本仓第一版就把 Batch >272K 的输出价抄成了 $50，被这两条断言逮住**）：

- `Batch` / `Flex` 的四项费率必须**严格等于** `Standard` 的一半；
- `Fast` 的四项费率必须**严格等于** `Standard` 的两倍。

另外两条口径容易互串，脚本里刻意分开打印：

- **总费用倍数**（同形状同 token 量下 Fast 长上下文 ÷ Batch 长上下文）≈ **4.0x**；
- 文章引用的 **8x** 是**输入费率之比**：Fast 长上下文 $40/M ÷ Batch 短上下文 $5/M。两者口径不同，不能互换。

## 已知边界

- 两个脚本都是**模拟/计算器**，不是对厂商计费系统的复刻。定价与阈值来自公开文档与第三方测算（见正文文末来源），厂商调价后需改 `TIERS`。
- `01` 的 token 用「4 字符 ≈ 1 token」粗估，只用于判断"窗口是否超预算"，不是精确 tokenizer；换真实 tokenizer 会改变触发时机，但不会改变"压缩会丢易失状态"这个结论。
- `01` 的检索是**精确 key 匹配**，没有做语义检索；真实 notes 子系统还要处理"同一 key 被多次覆盖"「检索相关性排序」等问题，脚本用覆盖写简化。
- `02` 的 272K 阈值判定**只看输入侧**（缓存输入单列便宜费率、不计入阈值）。若你的厂商口径是"输入+缓存输入合并判定"，改 `compute_cost` 里那一行 `over` 即可。
- `02` 未含图片输入计费、Batch 排队延迟、Fast 的额外配额限制等非 token 成本。

## 与正文的映射

- 问题 3（记忆机制）→ 脚本 1：`compaction` 侧检索返回 `None`、`notes` 侧拿回指针，就是"确定性 compaction 会丢易失状态"的最小可运行证据。
- 坑 1（把 compaction 当无损）→ 脚本 1 把 `--budget` 调大即可看到"两条管线都命中"，反过来证明"丢不丢取决于压不压缩"，所以不能假定摘要一定保真。
- 问题 5（272K 悬崖）→ 脚本 2 第一组演示：271K → 273K 仅多 0.7% 输入量，费用 2.01x，因为阈值作用于**整个请求**。
- 坑 2（以为只按超出部分加价）→ 脚本 2 的 `over` 判定写在整条请求上，可直接改参数验证。
- 坑 3（优化方向错：拼命少发 token，而不是让前缀可缓存）→ 脚本 2 第二组演示：200K 输入里 190K 命中缓存，单轮省 34.2%，30 轮省 $51.30。
