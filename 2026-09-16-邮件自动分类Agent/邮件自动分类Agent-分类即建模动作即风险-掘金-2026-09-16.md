# 邮件自动分类 Agent 为什么总在关键时刻掉链子

你大概率想过或写过这样一个东西：连上邮箱，新邮件进来自动归档、含「发票」的丢进账单夹、像垃圾的丢进垃圾箱。一眼看上去是 AI Agent 里最稳的一类——输入是文本，动作只是「挪个文件夹」，没有文件监控那种系统事件风暴，也没有客服那种实时对话。

但凡是把它当真用在跑的，几乎都踩过同一类坑：要么把老板的发票邮件判成垃圾、错过一个重要合同；要么把含身份证的邮件落库明文，埋下合规雷；要么一个 `expunge` 把重要邮件永久删掉、找不回来；要么连接断了 Agent 还以为自己成功了。

「读邮件 → 分类 → 移动」这个链路，真正的复杂度不在「怎么分类」，而在两层你一开始不会想到的地方：**分类层**（你对「邮件对象」和「规则冲突」建模错了）和**动作层**（Agent 对邮件落下的每一刀都是不可逆、且可能重复的）。本文把这两层拆开，配可运行代码讲清楚每个坑的根因和兜底。

代码已放在 `code/mail-agent/`：`01_mail_classifier.py` 是分类层，`02_action_safety.py` 是动作层，两个文件都带 `--self-test`，可以直接跑。配图在 `diagram/mail-agent/`。

## 〇、原理底座：邮件到底是「什么东西」

要真正填掉上面的坑，得先搞清楚一个事实：你处理的从来不是「一封邮件文本」，而是一个**带状态的对象**，跑在一套和你直觉不同的协议（IMAP）上。这块底层机制长什么样，直接决定了所有坑的根源。

### 1. 邮件是带状态的对象，不是纯文本

一封邮件至少有这些属于它自己的状态：UID（邮箱内稳定唯一标识）、`\Seen`/`\Flagged` 等 flags、它当前所在的 folder（INBOX / 账单 / 垃圾箱）、以及附件列表。分类 Agent 翻车的第一类根因，就是把「邮件」建模成了一个 `subject + body` 的字符串——于是它只能按关键词猜，一旦发件人身份、既有标签、归属文件夹这些上下文被忽略，就会犯「把老板的邮件判成垃圾」这种错。

所以正确的第一性建模是：**邮件 = 一个带 UID、flags、folder 归属、发件人可信度的对象**，分类是对「这个对象该去哪」的裁决，而不是对「这段文字像不像垃圾」的猜测。（配图见 `diagram/mail-agent/01-pipeline.svg`：全链路如何从「邮件对象」经过分类层、动作层落到 IMAP。）

### 2. IMAP 的「移动」和「删除」和你以为的完全不同

这是动作层翻车的根。IMAP 的几个语义，和本地文件系统的直觉是反着的：

- **`COPY` 保留原件**：把邮件从 A 复制到 B，A 里那份还在。IMAP 里没有「移动」这个原语，所谓 move = `COPY` 到目标 + 给原件标 `\Deleted`。
- **`\Deleted` 是可撤销的**：标了 `\Deleted` 只是打标记，邮件还在服务器上，客户端还能看到、还能救回来。
- **`EXPUNGE` 才是真删**：只有执行 `EXPUNGE`，带 `\Deleted` 的邮件才会被永久抹掉，且**不可恢复**。

很多人写「删除」时直接调 `expunge`，以为像 `os.remove` 一样能随手兜底——错。一次 `expunge` 清掉的可能是整个文件夹里所有被标记的邮件，且找不回。这就是为什么「删除走回收站 + 绝不 expunge」在邮件 Agent 里是一条铁律，而不是可选项。（配图见 `diagram/mail-agent/05-wrong-delete.svg`：左边 expunge 不可逆，右边 COPY→Trash 可找回。）

### 3. 触发是 at-least-once，必然重复

邮件的触发来源（IMAP `IDLE` 推送、定时轮询、或者网关 webhook）天然是 **at-least-once**：网络抖动会让同一次投递重放，轮询间隔重叠会让你把同一封邮件读两遍。`UID` 是邮箱内稳定的，但你的动作如果「收到就动」，就会对同一个 UID 移动两次、删除两次。这给了「UID 幂等去重」一个理论支点：消费者必须自己把 at-least-once 收敛成「有效一次」。（配图见 `diagram/mail-agent/07-idempotent-dup.svg`：无幂等重复执行 vs UID 幂等去重。）

### 4. 连接会断，断了的代价是「假成功」

IMAP 是长连接 + 网络协议。超时、服务端踢客户端、TLS 重协商，都会让连接在两次操作之间断掉。如果你在动作层写了 `try: ... except: pass`，连接失败时 Agent 不报错、日志一片绿，你以为邮件分类好了——其实什么都没发生。这点和《AI 客服为什么翻车》里「工具返回了它就信、失败被静默吞掉」是**同一个根**：Agent 和真实世界的交界处没有被正确建模。（配图见 `diagram/mail-agent/06-silent-failure.svg`，呼应 #23。）

## 一、先给结论：邮件 Agent 的不稳定，根因是对「邮件对象」和「不可逆动作」建模错了

把「邮件分类」当成一个「读文本、打标签」的简单任务，是一个危险的错觉。它有两个共享总根：

- **分类层**：你把邮件当成「无状态的文本片段」，于是白名单发件人被评分误杀、隐私在落库前没脱敏、多条规则打架时随执行顺序漂移。
- **动作层**：你把 IMAP 的「移动/删除」当成「本地文件操作」，于是 `expunge` 不可逆删信、断连被静默吞成假成功、at-least-once 重复触发重复动作。

于是「邮件自动分类 Agent」的稳定，取决于你能不能在两个地方各架一道闸：

```
邮件对象 ──▶ [分类层 Classifier] ──▶ 白名单/规则裁决/隐私脱敏 ──▶ Verdict(去哪/是否保护)
                                          │
                                          ▼
                              [动作层 Actioner] ──▶ 白名单/dry-run/回收站/幂等 ──▶ IMAP
```

下面按「分类层」和「动作层」两个失败模式，把坑一个一个说清楚。

## 二、失败模式 A：分类层把「该保护的」和「该拦的」搞反

分类层不碰真实邮件，但它是后面所有动作的输入。它一旦判错，动作层执行得再安全也是「安全地做错事」。

### 坑 1：误标垃圾，把老板的邮件判成垃圾

最经典的事故：你写了一条规则「正文含『中奖/优惠/免费』就丢垃圾箱」，结果老板发来一封「发票已开，优惠码见附件」，里面恰好有「优惠」二字，直接进垃圾箱，你三天后才发现错过了合同节点。

根因是对「发件人可信度」完全没建模——你只看了文本，没看是谁发的。看这张对比图（`diagram/mail-agent/02-mislabel-spam.svg`）：左边纯关键词评分把老板邮件误杀，右边白名单发件人优先级高于一切评分规则。

**解法是「白名单优先」这道闸，且它必须排在所有垃圾规则之前**：

```python
def classify(self, mail: Mail) -> Verdict:
    masked = mask_text(mail.body)
    # 1) 白名单优先于一切规则与评分（防误标垃圾的核心闸）
    if mail.from_addr in self.whitelist:
        return Verdict(mail.uid, "normal", mail.folder,
                       reason=f"白名单发件人 {mail.from_addr}，原样保留",
                       masked_body=masked, protected=True)
    # 2) 规则冲突：按优先级依次裁决……
```

`01_mail_classifier.py` 的 self-test 验证了这件事：一封 `from=boss@company.com`、正文满是「优惠/中奖/立即领取」的邮件，仍被判 `normal` 且 `protected=True`。**白名单不是锦上添花，是分类层的保命闸**——任何评分、任何规则，都不得越过它。

### 坑 2：隐私泄露，含身份证的邮件落库明文

第二类隐蔽事故：你为了做「智能归档」把分类后的邮件 body 落进自己的数据库/向量库，却忘了里面的身份证号、银行卡号、`api_key`。等合规审计或数据泄露时才发现，整库明文躺着几万条 PII。这比误标垃圾更麻烦——误标还能捞回来，明文泄露是既成事实。

根因是「落库前脱敏」这道工序被默认省略了。分类层既然已经拿到了 `body`，它就该是唯一一个「在写入任何外部存储之前」的关卡。看这张图（`diagram/mail-agent/03-privacy-leak.svg`）：左边明文直接落库，右边在落库前 `mask_text` 遮盖。

脱敏要覆盖三类最常见的 PII，且保留足够格式用于调试/审计：

```python
ID_CARD_RE = re.compile(r"\b\d{17}[\dXx]\b")
BANK_CARD_RE = re.compile(r"\b\d{16,19}\b")
SECRET_RE = re.compile(r"(?:api[_-]?key|secret|token|password)\s*[:=]\s*\S+", re.I)

def mask_text(text: str) -> str:
    text = ID_CARD_RE.sub(lambda m: m.group(0)[:4] + "***********" + m.group(0)[-2:], text)
    text = BANK_CARD_RE.sub(lambda m: m.group(0)[:4] + "********" + m.group(0)[-4:], text)
    text = SECRET_RE.sub(lambda m: m.group(0).split("=")[0].split(":")[0] + "=***REDACTED***", text)
    return text
```

身份证保留前 4 后 2（如 `1101***********51X`）、银行卡保留前 4 后 4、密钥整体打码。`classify` 返回的 `Verdict.masked_body` 才是可以安全落库的那份。self-test 断言：原文里的身份证、银行卡、`sk-abc123def` 在 `masked_body` 中一个都不剩。

### 坑 3：规则冲突，同一封邮件命中多条规则随顺序漂移

第三类坑最阴：你配了「发票 → 账单夹」和「中奖 → 垃圾箱」两条规则，某天来了一封「发票与中奖通知」——同时命中两条。如果你的实现是「遍历 `rules`，谁先 `append` 谁先赢」，那改个配置顺序、换个加载顺序，同一封邮件今天进账单、明天进垃圾箱，行为完全不可复现。

根因是规则之间缺一个**确定性的裁决序**。解法不是「小心别写错顺序」，而是把裁决序从「代码执行顺序」提升为「显式优先级字段」：

```python
self.rules = sorted(rules, key=lambda r: r.priority)   # 高优先级在前，priority 越小越优先

def classify(self, mail: Mail) -> Verdict:
    # ...
    for r in self.rules:                                # 已按 priority 排好
        if self._matches(mail, r.pattern):
            label = "spam" if r.is_spam else "classified"
            return Verdict(mail.uid, label, r.folder,
                           reason=f"命中规则[{r.name}](优先级 {r.priority})",
                           masked_body=masked)
```

看这张图（`diagram/mail-agent/04-rule-conflict.svg`）：左边无优先级、随执行顺序漂移，右边按 `priority` 确定性裁决。self-test 验证：同时含「发票」(优先级 1) 和「中奖」(优先级 5) 的邮件，稳定落到「账单」而非「垃圾箱」。**裁决序必须来自数据（优先级字段），不能来自代码顺序**——否则规则一多，没人能说清某封邮件会去哪。

## 三、失败模式 B：动作层对真实邮件落下的每一刀

分类层只产出「建议」(`Verdict`)，真正危险的是动作层——它动的是你得罪不起的真实邮件。

### 坑 4：一个 `expunge`，永久删掉重要邮件（最危险）

动作层最致命的事故：你实现「删除垃圾邮件」时，把 IMAP 的 `expunge` 当作「清空回收站」随手调用。结果某封本该进 Trash 的重要邮件，被 `expunge` 连同 `\Deleted` 标记一起永久抹掉——IMAP 里 `expunge` 不可恢复，服务商也不给你留后悔药。

根因是把 IMAP 的「删除」当成了本地文件的「删除」。看这张图（`diagram/mail-agent/05-wrong-delete.svg`）：左边「直接 expunge」0.1 秒清空不可逆；右边「三道闸」每一刀都能拦。

动作层防误删，要三道闸叠加，缺一不可：

**第一道闸：白名单优先。** 命中白名单的邮件，任何移动/删除规则都碰不了，优先级高于一切。

**第二道闸：`dry-run` 默认开启。** 没显式 `--apply`，引擎只报告「我会做什么」，绝不发任何 IMAP 命令。这是防止手滑的最后保险。

**第三道闸：删除走回收站，绝不 expunge。** 删除 = `COPY` 进 `Trash` + 给原件标 `\Deleted`，原件仍在服务器、可恢复。

```python
def delete(self, mail: Mail) -> str:
    if mail.uid in self.processed:
        return "skipped:idempotent"
    if self._whitelisted(mail):
        return "protected:whitelist"
    if self.dry_run:
        return "dry-run:no-op"
    try:
        self.imap.health_check()
        self.imap.copy(mail.uid, mail.folder, self.trash)   # COPY 进回收站
        self.imap.store_del(mail.uid, mail.folder)          # 标 \Deleted（可撤销）
        # 关键：不调用 self.imap.expunge()，所以没有永久删除
    except Exception as e:
        raise ActionAlert(f"delete({mail.uid}) 失败: {e}")
    self.processed.add(mail.uid)
    return f"deleted:{self.trash}"
```

`02_action_safety.py` 的 self-test 验证了三件事：白名单邮件原样保留；`dry-run` 不产生任何 IMAP 命令；`--apply` 时删除确实进了 `Trash`、且 `expunged` 列表为空（从未调用 `expunge`）。`expunge` 在「被事件驱动自动执行」的 Agent 里，就是定时炸弹。

### 坑 5：连接断了，Agent 还以为自己成功了

动作层第二隐蔽的坑：IMAP 连接在两次操作之间断开（超时、被服务端踢、TLS 重协商），你的 `move`/`delete` 抛 `ConnectionError`。如果你为了「别让 Agent 崩」写了 `except Exception: pass`，日志一片绿，你以为邮件分类好了——其实一次都没动。等用户问「我的邮件怎么没归档」，你才发现有几百封卡在 INBOX。

这和《AI 客服为什么翻车》里「工具返回了它就信、失败被静默吞掉」是**同一个根**：Agent 和真实世界的交界处（这里是 IMAP 连接）没有被正确建模。看这张图（`diagram/mail-agent/06-silent-failure.svg`，呼应 #23）。

**解法不是「多 try 几次」，而是「失败必须显式可见」**——定义一个 `ActionAlert`，任何 IMAP 异常都 wrap 成它抛出去，绝不吞：

```python
class ActionAlert(Exception):
    """动作执行失败时必须显式抛出，禁止静默吞掉。"""

def move(self, mail, dest):
    # ...
    try:
        self.imap.health_check()              # 断连这里就抛 ConnectionError
        self.imap.copy(...)
        self.imap.store_del(...)
    except Exception as e:
        raise ActionAlert(f"move({mail.uid}->{dest}) 失败: {e}")
```

self-test 里把 `FakeIMAP.connected` 置为 `False`，断言 `move` 必然抛出 `ActionAlert`——**连接失败绝不能变成假成功**。上层调度看到 `ActionAlert` 才该重试或告警，而不是在「以为成功」的状态里越走越远。

### 坑 6：重复触发，同一封邮件被移动 N 次

动作层第三坑：at-least-once 触发下，同一封邮件可能进动作层两遍。如果第一次已经把它从 INBOX 移到「账单」，第二次再对同一个 UID 执行 `move`，要么因为原件已被标 `\Deleted` 而报错，要么在边界情况下把它从「账单」又搬到别处，行为不可预期。

根因是动作层没有「这封我已经处理过」的记忆。解法是一道独立的**UID 幂等闸**，它和「防抖」不是一回事（邮件这里没有时间窗口概念，只有 UID 维度）：

```python
def move(self, mail: Mail, dest: str) -> str:
    if mail.uid in self.processed:          # UID 幂等：同 uid 只处理一次
        return "skipped:idempotent"
    # ... 白名单 / dry-run / 实际动作 ...
    self.processed.add(mail.uid)
    return f"moved:{dest}"
```

看这张图（`diagram/mail-agent/07-idempotent-dup.svg`）：左边无幂等、重复触发各落一次动作；右边用 `processed` 集合去重，同一 UID 第二次直接跳过。self-test 验证：连续两次对 `u3` 调 `move`，第二次返回 `skipped:idempotent`，且 IMAP 命令只发了 2 条（一次 move 的 COPY + STORE，不是 4 条）。`processed` 在生产里要跨进程持久化（如 Redis / 数据库），否则进程重启幂等就失效——这是落地的隐形坑，本文字节码用内存集合演示原理，生产请换成持久存储。

## 四、收束：两个失败模式，一个总根

回到开头的故障树：

| 大症状 | 失败模式 | 根因（共享总根） |
|---|---|---|
| 邮件 Agent 上线就分错 | A. 分类层误标/泄露/冲突 | 把邮件当「无状态文本」建模 |
| 邮件 Agent 搞丢/假动邮件 | B. 动作层误删/静默/重复 | 对「不可逆动作」没有分层兜底 |

解法不是「更努力地调提示词或分类模型」，而是承认：**分类层负责产出「可信、可保护、已脱敏」的裁决，动作层负责让每一刀都可拦截、可找回、可去重**。二者之间那道清晰的边界（白名单优先 + dry-run + 回收站 + 幂等 + 失败告警），才是邮件 Agent 能不能活过第一周的关键。

本文配的两个脚本，把这套边界落成了可运行代码：`01_mail_classifier.py` 用「白名单优先 + 优先级裁决 + 落库前脱敏」守住分类，`02_action_safety.py` 用「白名单 + dry-run + 回收站 + UID 幂等 + 失败告警」守住动作。直接 `--self-test` 能看到每道闸的行为。

## 五、结尾钩子

如果你读了我前一篇《文件监控 Agent 为什么总掉链子》和更早的《AI 客服为什么翻车》，会发现这三件事是同一个根：Agent 不可靠，往往不是「模型不够聪明」，而是它和真实世界的交界处（工具调用、文件系统事件、邮件协议）没有被正确建模。客服翻在「工具返回了它就信」，文件监控翻在「事件来了它就动」，**邮件 Agent 翻在「邮件是文本、IMAP 是本地文件」这两个错觉上**。

下一个最容易翻车的 Agent 是什么？我赌是那些「替你做决定并自动执行跨系统动作」的——自动回复、自动下单、自动改数据库。它们的交界更复杂，兜底更难，而且错的代价不再是一封邮件，而是一笔钱、一条记录。这个系列我会接着拆。

## 六、本篇做了什么 / 对谁有用

- **做了什么**：把「邮件自动分类 Agent」拆成分类层（白名单优先/规则优先级裁决/落库前隐私脱敏）和动作层（白名单/dry-run/回收站/UID 幂等/失败告警），先讲清原理底座（邮件是带状态对象、IMAP 的 COPY/\\Deleted/EXPUNGE 语义、at-least-once 触发、断连假成功），再逐个坑给根因 + 可运行代码 + self-test，配 7 张原理图。
- **对谁有用**：① 想写邮箱自动归档/过滤/智能助理的人；② 做 RPA、办公自动化、邮件网关的工程师；③ 任何要「让 Agent 安全地动真实数据」的开发者。
- **不重述原理的踩坑清单**：① 白名单发件人必须排在所有垃圾规则之前，否则老板邮件会被误杀；② 落库前 `mask_text` 脱敏身份证/银行卡/密钥，明文落库是合规事故；③ 多规则冲突用显式 `priority` 字段裁决，不能靠代码顺序；④ 删除走 COPY→Trash + 标 `\Deleted`，绝不 `expunge`；⑤ 连接失败必须抛 `ActionAlert`，禁止 `except: pass` 假成功（呼应 #23）；⑥ 用 UID 幂等去重，at-least-once 触发必然重复。

## 七、本文不承诺什么（铁律 #6）

- 不承诺「用了这套代码你的邮件 Agent 就永不翻车」。符号链接邮件、跨邮箱 UID 不稳定、服务端 `EXPUNGE` 策略差异等边界，仍需要你结合自己的邮件服务商校准。
- 不承诺任何量化收益（如「省 90% 误判」「提速 N 倍」）——白名单名单、优先级数值、脱敏正则都是按你的场景配的，没有通用最优值。
- 文中 `processed` 幂等集在生产里必须换成持久化存储（Redis/DB），否则进程重启幂等失效；本文为演示原理用内存集合，不自称「生产可用」。
