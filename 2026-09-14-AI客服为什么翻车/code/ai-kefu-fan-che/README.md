## 重要说明：这是「机制模拟器」，不是真实模型调用

文章讲的四类翻车（延迟 / 幻觉 / 上下文污染 / 静默失败），其**真实事故数字**来自公开来源（BestHub、Traversaal、Klarna、LangChain 失败模式定性分析等，见文章参考来源）。脚本不调用任何 LLM，而是用可配置参数**复现这四类机制**，让你在本地看到"为什么会翻车"，并能随参数变化观察失败率怎么涨。脚本默认参数贴近事故量级，但**不是某家公司的真实配置**。

## 01 · 最小客服 agent-loop

**为什么写它**：客服 agent 在用户眼里就是"一句话进、一句话出"。但中间藏着一条长链路——意图识别 → RAG 检索 → 工具调用（查订单/退款）→ 生成。这一条链路每多一个环节，延迟和出错面就多一分。脚本把这条链路跑出来，并逐轮测量 TTFT、记录工具调用、检测两类幻觉（基于错误知识作答、生成非法退款 ID）。

**实测输出**（`python3 01_agent_loop.py --demo`）：
```
轮 | 意图    | TTFT(ms) | 幻觉 | 静默失败 | 回复
 1 | refund  |   3200.0 | False |    False | 已为您提交退款，单号 RF2301595691……
 2 | order   |   3200.0 | True  |     True | 您的订单已发货，预计明天送达。（实为推测）
 4 | refund  |   3200.0 | True  |     True | 根据规则，您的情况可以这样处理……（基于错误知识作答）
```
第 2、4 轮分别演示了"静默失败"（工具报错被圆成正常结果）和"幻觉"（检索到无关文档仍作答）。

**接入点**：改 `CustomerServiceAgent(retrieval_ms=, tool_ms=, gen_ms=, retrieval_error_rate=, silent_fail_rate=)` 即可把链路调长/调短、把出错率调高/调低，观察对下游的影响。

**CI 门禁**：`--self-test` 断言：结构字段齐全、合法退款不判幻觉、检索到错误文档判幻觉、工具静默失败被标记、第 6 轮标记上下文污染、默认链路 TTFT > 2000ms。

## 02 · 四类翻车率批量评估

**为什么写它**：单轮 demo 只能看个例，批量跑才能谈"率"。脚本用 01 的 agent 跑 N 段多轮对话，统计四类失败率，并和文章里的公开真实数字并列打印。

**实测输出**（`python3 02_failure_eval.py --n 2000`）：
```
会话数            : 2000
总对话轮次        : 13146
平均 TTFT         : 3497.9 ms
转人工率(代理)    : 79.8%  (TTFT≥3000ms)
幻觉率            : 26.5%
静默失败率        : 17.5%
上下文污染率      : 19.6%  (第6轮起)
```
对照公开真实数字：BestHub 静默失败 23%、Traversaal 74% 企业回滚。模拟复现与真实事故同量级，说明机制成立、不是个例。

**接入点**：`eval_sessions(n=, retrieval_error_rate=, silent_fail_rate=, handoff_threshold_ms=)` 调整样本量与参数，看失败率如何随链路变长、出错率变高而恶化。

**CI 门禁**：`--self-test` 断言：高延迟下转人工率 > 50%、静默失败率在 15%–35%、幻觉率与上下文污染率 > 0、平均 TTFT > 3000ms。

## 已知边界

- 脚本复现的是**机制**，不是某家公司的真实流量与模型行为；真实事故数字以文章参考来源为准，脚本不反向工程未公开的系统配置。
- TTFT 采用"延迟预算"（检索 + 工具 + 生成首字配置值之和），不做真实 wall-clock sleep，目的是让批量评估可瞬时复现、CI 可跑。
- 幻觉/静默/污染率对随机种子敏感；`--self-test` 用固定种子保证可复现，手动 `--n` 跑会得到相近但略有波动的数值（同量级）。
